## My Reflection
> **DRAFT written by the coding agent from the sprint record - Siméon: please rewrite in your own words before submitting.**

**Specification agent.** The contract (specification, API, UI and test plans) was produced with a chat agent before any code and reviewed by Yanis in #56. It was a solid base: every implementation PR could point to an AC and a test ID. It was not perfect: UNIT-01 said 14 allowed transitions while the matrix has 20, and two dashboard drill-downs could not satisfy L4-BR-21 as written (tickets without an IT priority; action-based cards without a list total). Those became CL-01 and CL-02.

**Coding agent.** Claude Code worked one Issue per branch and PR, wrote the failing tests first and committed them before the code, and saved logs with commit hash, date and exit code. It stopped and asked when the contract was contradictory (edit rights FR-02, clientRequestId scope, Dashboard as landing page vs. Lab 1-3 tests) instead of deciding alone. It also found problems through its own evidence: mid-word wrapping and clipped buttons in screenshots (CL-03), a select overflowing at 768px, and that 3 Lab 2/3 E2E failures came from local account state, not from code.

**What I corrected or decided.** The effectivePriority filter (CL-01); keeping CL-02 after Yanis questioned it; Dashboard as landing page with a minimal CHG-06 instead of keeping the old landing; moving the clientRequestId race fix out of a PR under review into #55; a separate test database and a clean demo database for the final evidence.

**Process.** Every PR was reviewed by Yanis (reviewer.md). #57 and #59 were merged before his approval and approved afterwards; from Batch A on, PRs were merged only after an APPROVED review.

**What I would do differently.** Isolate the test database from day one (shared-DB pollution cost time in Lab 4), keep E2E credentials in fixtures from the start, and split housekeeping commits (reviewer log, logs) into their own small PRs, as Yanis asked on #63.
