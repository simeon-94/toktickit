# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

This sprint I'm building the part of TokTickIT where a Requester can actually create a support
ticket, attach files to it, and find it again afterward. There's no real login system yet, so
I'm using a temporary "pick who you are" screen instead.

## 2. Stakeholder Request Interpretation

Basically the IT department wants a working form for end users to submit support tickets:
pick a category, describe the problem, attach evidence, set a priority, submit. After that they
need to be able to find their own tickets again (search/filter), open one, and manage its
attachments. One user should never be able to see someone else's tickets. Since real
authentication isn't built yet, I need a fake "select your identity" screen just so I can test
this as different users.

## 3. Scope

### Included
- Development Requester Selection screen (fake login, testing only)
- Create Ticket screen with validation
- My Tickets screen: list, search, filter, sort, pagination
- Requester Ticket Detail screen (read-only info + attachments)
- Attachment upload, download, and soft removal
- Ownership checks (a Requester only ever sees their own stuff)

### Excluded (on purpose, not forgotten)
- Real authentication (login, passwords, sessions, tokens) — that's Lab 3
- IT Staff dashboard / anything an IT Staff member would do
- Public Comments, Internal Notes, Actions Taken
- Any ticket status change beyond the initial "New" status
- Admin stuff (managing users, roles, reference data)

## 4. Functional Requirements

- FR-01: Pick a Development Requester identity before doing anything else in the app.
- FR-02: Create a new ticket by filling in Category, Related System, Summary, Description, and
  Requested Priority.
- FR-03: Attach up to 5 files to a ticket, either while creating it or afterward.
- FR-04: Get a unique Ticket Number back automatically once the ticket is created.
- FR-05: See a paginated list of your own tickets in My Tickets.
- FR-06: Search your tickets by keyword (ticket number or summary text).
- FR-07: Filter your tickets by Category, Requested Priority, IT Priority, and Current Status.
- FR-08: Sort the ticket list by different columns.
- FR-09: Open a Ticket Detail screen and see the full ticket info.
- FR-10: Add a new attachment to a ticket you already created, from Ticket Detail.
- FR-11: Download an attachment that hasn't been removed.
- FR-12: Soft-remove one of your own attachments.
- FR-13: Get blocked from viewing or touching a ticket/attachment that isn't yours.
- FR-14: See clear loading / empty / no-results / error states everywhere data loads.
- FR-15: Use the app comfortably on desktop, tablet, and mobile.

## 5. Business Rules

- BR-01: Ticket Number is generated by the backend, unique, format
  `TKT-{year}-{6 digit number}` (e.g. `TKT-2026-000123`). I picked this format since the
  labsheet just says "unique", not an exact format.
- BR-02: A new ticket always starts as Current Status "New".
- BR-03: The Development Requester selector is only for testing — not real auth. Gets replaced
  by real login in Lab 3.
- BR-04: The selected Requester is remembered on the frontend (kept in memory / local storage)
  and sent along with requests so the backend knows who's asking.
- BR-05: Switching to a different Requester via "Change Requester" reloads all their data — you
  shouldn't see leftover data from the previous Requester.
- BR-06: A ticket belongs to exactly one Requester (whoever created it) and only that Requester
  can read or touch it.
- BR-07: My Tickets only ever returns tickets owned by whoever is currently selected — never
  someone else's, even if you try to request them directly by ID.
- BR-08: Search is case-insensitive and matches partial text in the ticket number or summary.
- BR-09: Filters can be combined — a result has to match all active filters at once, not just
  one.
- BR-10: Ticket list defaults to newest-first by Created Date unless you pick another sort.
- BR-11: Pagination defaults to 10 tickets per page.
- BR-12: Summary is required, 3–150 characters (trimmed). Description is required, 10–2000
  characters (trimmed). I picked these limits so the form isn't annoyingly strict but still
  catches empty/garbage input.
- BR-13: Submitting with missing/invalid required fields never hits the backend — the frontend
  catches it first.
- BR-14: If ticket creation fails on the backend, whatever the Requester typed stays in the
  form. Nobody should have to retype everything because of a server hiccup.
- BR-15: Attachments: JPG/JPEG, PNG, WEBP, or PDF only, 5 MB max per file, 5 active attachments
  max per ticket.
- BR-16: A bad file type or an oversized file gets rejected with a clear message and doesn't
  count toward the 5-file limit.
- BR-17: If the ticket saves fine but a specific attachment upload fails, the ticket still
  exists — you just see an error for that one file and can retry it.
- BR-18: Removing an attachment is a "soft" removal — the file's name/size/date stay visible,
  marked as removed, but it can't be downloaded or previewed anymore. Basically like a recycle
  bin, not permanent deletion.
- BR-19: Inactive Development Requesters don't show up in the selector dropdown.
- BR-20: If there are zero active Development Requesters, the selector shows an empty state
  instead of just breaking.
- BR-21: Zero search/filter results is a different state ("no results, try adjusting filters")
  than having zero tickets at all ("you don't have any tickets yet").

## 6. UI Specification Summary

Everything reuses the Zen Green theme from Lab 1 — same primary green header, same pale-green
success/selected color, same soft-gray read-only fields, dark red for errors. New screens for
this lab: Development Requester Selection, Create Ticket, My Tickets, Requester Ticket Detail.
Every one of them needs a loading state, an empty/no-results state, and an error state, and has
to work on desktop (≥992px), tablet (768–991px), and mobile (<768px) without anything getting
cut off or causing horizontal scroll. Full detail in ui-spec.md.

## 7. Data Changes

- **DevRequester**: id, name, email, isActive, createdAt
- **Category**: id, name (unique) — already exists from Lab 1
- **RelatedSystem**: id, name (unique)
- **Ticket**: id, ticketNumber (unique), requesterId → DevRequester, categoryId → Category,
  relatedSystemId → RelatedSystem, summary, description, requestedPriority
  (LOW/MEDIUM/HIGH), itPriority (empty for now), currentStatus (defaults to "New"),
  createdAt, updatedAt
- **Attachment**: id, ticketId → Ticket, fileName, storedFileName, mimeType, sizeBytes,
  isRemoved, removedAt, uploadedAt

Indexes: unique on `ticketNumber`, plus indexes on `requesterId`, `currentStatus`, and
`categoryId` since those get queried/filtered on constantly.

## 8. API Contract

(Full details — request/response bodies, exact status codes — live in api-spec.md. Quick
summary here.)

- `GET /api/dev-requesters` — active Development Requesters
- `GET /api/categories` — categories (from Lab 1)
- `GET /api/related-systems` — active related systems
- `POST /api/tickets` — create a ticket for whoever's selected
- `GET /api/tickets?search=&category=&priority=&status=&sort=&page=` — your own tickets,
  filtered/sorted/paginated
- `GET /api/tickets/:id` — one ticket, only if you own it
- `POST /api/tickets/:id/attachments` — upload a file to a ticket you own
- `GET /api/tickets/:id/attachments` — list attachment metadata for a ticket you own
- `GET /api/attachments/:id/download` — download an active attachment you own
- `DELETE /api/attachments/:id` — soft-remove an active attachment you own

## 9. Acceptance Criteria

- AC-01: Given valid ticket data, when I submit Create Ticket, then the ticket saves and I see
  the generated Ticket Number.
- AC-02: Given no Requester is selected, when I try to open My Tickets, then I get sent to the
  Requester Selection screen instead.
- AC-03: Given I'm Requester B, when I try to load a ticket that belongs to Requester A, then I
  get nothing back.
- AC-04: Given the Summary field is empty, when I submit, then I see a field error and no API
  call happens.
- AC-05: Given I have tickets but my search matches none of them, then I see a "no results"
  message — not the same screen as having zero tickets total.
- AC-06: Given I have zero tickets, when I open My Tickets, then I see an empty state with a
  Create Ticket button.
- AC-07: Given a valid JPG under 5MB, when I attach it, then it uploads and shows up in the
  list.
- AC-08: Given a .exe file, when I try to attach it, then it's rejected with a clear message.
- AC-09: Given an attachment was soft-removed, when I try to download it, then it's blocked but
  I can still see its name marked "removed".
- AC-10: Given the backend is down, when I submit Create Ticket, then I get a safe error message
  and my form data isn't wiped.
- AC-11: Given a mobile screen, when I open My Tickets, then everything's usable, nothing
  scrolls sideways.
- AC-12: Given there's an inactive Requester in the database, when the selector loads, then that
  Requester isn't in the dropdown.

## 11. Assumptions and Decisions

- Went with `TKT-{year}-{6-digit number}` for the ticket number since the labsheet only says
  "unique," not an exact format.
- Default page size for My Tickets is 10 — kept it simple, no page-size picker for this lab.
- Attachments get saved on disk under a generated safe filename, not the original one, to avoid
  weird filename collisions. The original name is still shown in the UI.
- IT Priority stays empty for now since setting it is something IT Staff does, and that's not
  part of this sprint.
- The Requester selection lives only in the frontend (not a real session), since it's clearly
  labeled as a testing tool, not real auth.
